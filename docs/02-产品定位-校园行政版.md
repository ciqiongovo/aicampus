# 产品定位（校园行政版）

*2026-11-12 · 基于 InfoAgent / AgentiCampus 改写*

---

## 一、一句话定位

**它不是一个"学生助手"，是一个学生组织的信息办公室。**

学生会的活，一大半不是"做活动"，是"找东西、记东西、交代东西"。这个系统只干这三件事。

---

## 二、出身交代

不是从零开始。同一套内核在技术马拉松上做成过学生版（InfoAgent，Windows 便携版可运行，153 个源文件、213 项测试），跑通过完整闭环。

**改的只有服务对象**：从"一个学生怎么安排自己的学习"，改成"一个组织怎么把信息变成可执行的分工"。

内核没变：多源汇集 → 理解与筛选 → 出处可查 → 落成行动。

---

## 三、行政的三个卡点

1. **信息不进同一个地方。** 通知在邮箱，讨论在群，宣传在公众号，别的学校怎么干在人家官网上。找一次信息，翻四个地方。
2. **看见了不等于办了。** 群里的消息刷过去就是刷过去了，没有分派、没有截止、没有跟进。事情不是没人看见，是没人认领。
3. **办事靠记忆，不靠档案。** 换届即失忆。去年迎新踩过的坑，今年再踩一遍；别的学校早就解决过的问题，我们重新试错。

---

## 四、产品形态：三个工作台，一条采集线

| | 名称 | 给谁用 | 解决什么 |
|---|---|---|---|
| ① | **收件台** | 部长／干事 | 校内的通知、邮件、群消息汇到一处，筛出"今天该办什么"，一键转待办、分派人 |
| ② | **对标库** | 策划组 | 别的学校同类活动怎么做的，按主题聚类，随时可查 |
| ③ | **筹备台** | 项目负责人 | 一场活动从立项到收尾的倒排期：任务、截止、材料、复盘 |
| ＋ | **方案体检** | 负责人 | 方案定稿前，系统给出这类活动常见的失败原因和被质疑点，带出处 |

一条铁律贯穿四个部分：**任何一条结论，都能点回原文。** 没有出处的内容不写。

---

## 五、功能取舍：砍什么，为什么

原来的学生版有十个模块。行政版只留六个，其余明确砍掉，不做"看起来功能很多"。

| 原功能 | 去留 | 理由 |
|---|---|---|
| 多源信息汇集（邮箱／平台） | **留，扩** | 行政的主战场就是这里，还要加上群聊、公众号、外校官网 |
| 文档解析 + 向量知识库 | **留，改用途** | 学生版查课件；行政版查章程、往届策划、场地规定、报销流程 |
| Hybrid RAG 问答 | **留** | "去年迎新是谁负责场地"这种问题，现在的答案是"问上一届" |
| 待办与日程 | **留，改结构** | 从"我个人要做的事"改成"这件事归谁、卡在哪一步" |
| 日报／晨间播报 | **留，降级** | 从个人播报改成"今日行政要点"，去掉语音闹钟 |
| 反馈学习、推荐排序 | **留** | 但权重按部门调，不按个人喜好 |
| **引导式作业教学（苏格拉底提问、脚手架、形成性评价）** | **砍** | 这是学生版的核心，但对行政零用处。留着只会让评审觉得我们在凑功能 |
| Android 客户端 | **砍** | 行政场景在电脑上完成，手机上只需要收通知 |
| 语音播报、原生闹钟 | **砍** | 是学生版的记忆点，不是行政的痛点 |
| 反推荐引擎 | **留，重建语料** | 见下 |

**砍掉"作业教学"这一条要特别说明**：它不是不重要，是它太好了，好到会把这个项目拽回"学习工具"。定位必须干净。

## 六、跨校采集那条线（这条线是新的）

这是主席指的方向，也是这一版和上一版最实质的差别。

### 6.1 采什么

| 层级 | 来源 | 采什么 | 稳定性 |
|---|---|---|---|
| 一级 | 兄弟高校学生会／研会／团委公众号 | 推文正文、发布时间、活动类型 | 正文稳，列表需给定账号 |
| 二级 | 高校官网"学生活动""通知公告"栏目 | 活动通知、时间地点、报名方式 | 稳定，栏目结构固定 |
| 三级 | B 站／抖音／小红书官方号 | 宣传视频、活动热度 | 不稳定，作为补充 |

### 6.2 抽什么字段

活动名称、主办方、时间、地点、面向对象、参与方式、宣传文案、组织形式（比赛／讲座／市集／志愿服务）、是否有赞助、传播数据。

抽完不是堆一坨文本，是**结构化入库**，这样才能"按主题查"。

### 6.3 怎么用

按主题聚类：迎新、毕业季、歌手赛、志愿服务、学术沙龙……

我们要办某类活动时，先看同类：别人怎么定的时间地点、宣传文案什么调性、有没有踩坑的痕迹（比如"因场地调整"这种二次通知）。

### 6.4 诚实说清楚的两条边界

1. **公众号不能"全自动发现"。** 系统不会凭空知道全国有哪些公众号、哪些发活动。必须由人给定账号清单（比如先给 30 个兄弟高校的学生会号），系统负责持续抓、持续更新。这是现实限制，不是设计缺陷。
2. **抓的是公开内容**，不做登录态抓取、不绕过任何权限，也不保存个人信息。

## 七、和学生版是什么关系

同内核，两种形态。不是两个项目，也不是"换了个皮"。

| | 学生版 | 行政版 |
|---|---|---|
| 服务对象 | 一个学生 | 一个组织 |
| 信息终点 | 我今天的安排 | 这件事归谁、办到哪一步 |
| 知识库内容 | 课件、作业 | 章程、往届材料、场地与报销规定 |
| 新增能力 | 教学辅导 | 跨校对标 |

对外表述时不要回避"这是同一套东西改的"——**能在四十八小时里做出学生版，本身就证明了这套内核是可复用的**，这正好是"借鉴价值"的证据。

---

## 八、这一版做什么，不做什么

**做（这一版的目标）**：

1. 收件台能跑通：真邮箱、真群聊 → 真待办
2. 对标库能跑通：30 个公众号 → 可查的案例库
3. 留痕能跑通：每条内容点得回原文

**不做（明确写进范围外）**：

- 不做全自动发文、不做替代现有办公系统
- 不做云端同步（本地优先，数据不出机器）
- 不做多校共享平台（先证明一个组织能用起来）

---

## 九、现在能说什么，不能说什么

- **能说**：东西是有的，能跑，代码和测试可查
- **能说**：路子是对的，同类组织换配置就能用
- **不能说**：用了之后省了多少时间——没有真实用户跑满一个周期，说数字就是编
- **要说**：现阶段的短板（数据库未加密、公众号列表需人工给、第三方接口会变），主动写在材料里，比被问出来强

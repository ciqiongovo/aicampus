## 三、一个待解决的依赖

`tools/im-connector/src/main/services/im/chatlog.ts` 依赖 **chatlog** 这个 Go 写的本地 HTTP 侧车（127.0.0.1:5030）。chatlog 已于 2025-10 被微信官方函件下架，现在是拿不到的。

好消息是这个文件本身写得克制——注释原话：「这里只依赖 HTTP，不关心它内部怎么解密；接其它实现（PyWxDump、自研 sidecar）时换掉本类即可。」

本地已有自研解密能力（`repos/b/wechat-decrypt-main`，frida 抓 key + 解密 20 个库，已跑通）。所以补一个 HTTP 适配层就能把 im-connector 复活。但**不建议**为了报名表去承诺群消息自动汇入：那意味着系统要读全班群聊，与「涉及师生个人信息的数据已脱敏」的承诺相冲，出问题的代价远大于收益。v3 报名表写「邮件与**转发的**消息汇入」就是这个考虑。

## 四、改造路线

**M1 跑起来（1 天）**
`app/` 内 `pnpm install` → `pnpm dev`，确认基线可启动、邮件事务可读、数据库迁移正常。不改业务。

**M2 对标库最小闭环（3–4 天，报名表第一卖点的最低可演示形态）**
新建独立模块 `app/src/main/services/benchmark/`，不塞进现有 mail 体系：
1. 订阅源：关注列表（20 所）→ 读本地微信库 → 链接入 `benchmark_source` 表
2. 抓取：`msedge --headless=new --dump-dom` + lxml 等价逻辑（已验证 6/6），Node 侧用 cheerio
3. 抽取：活动通知判定 + 7 字段（类型/主办方/时间/地点/对象/参与方式/宣传形式），走国内模型
4. 页面：按学校、类型、时间筛 + 三列并排对比 + 打开原文
验收：三十所清单里的任意一校，能点出它最近 10 篇活动，字段可读、链接可跳。

**M3 简报与排期（2–3 天）**
对标简报导出（带原文链接）；活动立项倒排 + 撞期提示。

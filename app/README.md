# 知枢 · 桌面端

高校公众号活动对标与决策支持。侧栏第一档只放这条主线上的板块——对标、JARVIS、
日程、待办、资料；面板、日报、邮件这些个人资讯工具收进「更多」，设置钉在最后。
九个板块平铺在侧栏时，第一眼看不出这个软件是干什么的。

技术栈：Electron 44 + React 18 + TypeScript + electron-vite + Ant Design 5，
数据库是 Node 内置的 `node:sqlite`（`DatabaseSync`），不依赖任何原生扩展。

产品说明与使用方式见仓库根目录的 [`../README.md`](../README.md)。

## 开发

```bash
npm install
npm run dev             # 开发模式（热更新）
npm run typecheck       # 主进程与界面两端类型检查
npm test                # 单元测试
npm run build           # 构建到 out/
npm run dist            # 打包 NSIS 安装程序 + 便携版
npm run dist:portable   # 只打便携版 exe（release/ZhiShu-<版本>-portable.exe）
```

Windows 上也有两个双击就能用的脚本：`启动知枢.bat`（选开发/启动/重建）与
`打包知枢.bat`（构建并打包，末尾打印 SHA-256）。

## 数据放在哪

`%APPDATA%\ZhiShu\zhishu.db`（macOS 是 `~/Library/Application Support/ZhiShu/`）。
目录名用英文而不是中文：这个路径会进 spawn 参数和 SQLite 连接串，中文在某些环节会出事。

第一次启动时，如果发现旧版 `InfoAgent/infoagent.db`，会用 `VACUUM INTO` 把整库搬过来一次。
用 `VACUUM INTO` 而不是复制文件，是因为 WAL 里可能还有没落盘的写入，拷主库文件会丢最后几条。
搬完不动旧库，删不删由用户决定。

**换版本不会丢数据**：数据库在 userData 里，跟程序目录分离；便携版 exe 换成新的一扔就行。

## 采集三条硬约束

写在这里是因为踩过，改代码前先看一眼。

1. **账号名必须加引号。** 查询是 `site:mp.weixin.qq.com "上海科技大学学生会"`。
   不加引号会被拆成三个词做与匹配，返回的全是别校的「学生会」稿子——实测 25 篇里只有 4 篇对。
2. **配额是硬的。** 一个出口 IP 连查 4–5 次就触发验证码。所以每个账号之间停 3.5–6.5 秒，
   连续两次被拦立刻停手，一次最多查五六个账号。别为了「快一点」把间隔改小。
3. **正文必须真渲染。** 公众号页面是 JS 外壳，直接拿源码是空的。主进程开隐藏窗口渲染，
   兜底用外部浏览器 `--headless=new --dump-dom`。

去重键是 `__biz + mid + idx`（`articleUrlKey()`），必须保留 `chksm`，否则同一篇会因为
分享来源不同被当成两篇。

## 抽取两套链路

- **规则**（`rule-extract.ts`）：不需要任何 key，装完即用。够拿到类型、时间、地点、主办。
- **模型**（`extractor.ts`）：配了 API key 后多出议程、特色环节、规模、可迁移性和依据。
  提示词里明确要求「特色环节与议程不重复」「规模只写原文数字，不换算」。

两边输出的字段结构一致，界面上不分来源，只在设置里显示当前走的是哪条。

## 什么算「一场活动」

规则抽取靠词表判活动，最容易出的错不是漏，是**把不是活动的稿子当成活动**。
实测 50 条已入库条目里 20 条不是活动：人物报道（「毕业生故事｜王宇瀚」）、
候选人公示、换届大会、月度汇总、学院介绍。它们标题里也有人、有日期，
正文里还写着「晚会」「毕业季」，一路骗过类型词表。

`offTopicReason()` 因此只在标题上判，分五类给理由（人物报道 / 名单公示 /
会议通报 / 合集汇总 / 招生与建制），并在命中后检查标题里有没有活动动词
（举办、报名、分享会……）——「优秀毕业生分享会」是真活动，「优秀毕业生胡豆豆」不是。

已经抽过的条目不会自动重判：那等于没打招呼就动用户的数据。数据体检里会列出
「按现在的规则不像活动」的条目，勾选后剔除，只删抽取结果，原文和链接都留着。

判活动还要算清**一场还是几篇**：同一场迎新晚会会发预告、招募、回顾三条。
表里的「8/7」是 8 篇推文合并成 7 场，按「类型 + 日期」合并；没写日期的各算一场——
两场都没写日期就分不出来，硬合并比虚高更糟。

## 简报：罗列之外还要做减法

`brief.ts` 只负责排版，把条目排成能念出口的样子；`compare.ts` 负责把条目压成
「各校在同一维度上的数」——规模中位数、提前预告天数、合办占比、最常办的类型。
两者共用同一批条目，所以表里的数和正文列出的条目永远对得上。

三条自律，改的时候别松：

1. **只统计有样本的维度。** 一条活动写了「200 人」、另一条没写，不能当成 0。
   分母只算写了的，覆盖率单列一栏说明这个中位数是按几条算的。
2. **样本不足两场不进对比表。** 一所学校只有 1 条时，「中位规模」毫无意义，
   但印在表里会被当成事实引用。这类学校只点名，不进表。
3. **列随数据走。** 实测 50 场活动里只有 2 场在原文写了参与人数——固定摆一列
   规模，满格都是「—」，看的人会以为抽取坏了。某项不足两所学校有数据就整列不出现，
   改为在结论里直说「这项原文普遍没写」。

结论句同理：写不出数字支撑的话一律不写，宁可比别人少说两句。

### 两种切法，问的不是同一个问题

`compare.schools` 按学校切：「谁办得多、谁预热早」。`compare.topics` 按活动类型切：
「迎新晚会别人怎么办的」。真到自己要办一场时，第二种才是能照着改的东西——
场地在哪、要不要抢票、请谁合办、有什么环节。

`buildTopics()` 的几条规矩：

- 同一场活动的预告 / 招募 / 回顾会各写一篇，按「学校 + 日期」合成一场，
  留下信息最全的那一条（非空字段最多，平手取发布最早的）。
- 少于两所学校的类型不进对照：一所学校的两场是它自己的重复，不是「别人怎么做的」。
- 场地与参与方式都先归一成类别（礼堂与剧场、体育场馆、活动中心；抢票、报名、扫码进群）。
  不归一的话，「逸夫楼报告厅」「东区体育馆」并排看只能看出名字不一样。
- 列同样随数据走，门槛是「至少两行、且不低于四分之一」：20 场里只有 2 场写了参与方式，
  单开一列会让人以为这是个可比的维度。

`report.ts` 生成自包含 HTML（样式内联、无外链、无脚本），双击能看，Ctrl+P 能印。
不走 CDN 也不引外链字体——别人电脑上能不能打开，不该取决于他有没有网。

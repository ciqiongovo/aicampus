# 行政版改造构想

*2026-11-12 · 基于 InfoAgent 现有能力，面向"AI 赋能校园行政"*

---

## 0. 一句话

**内核不动，换服务对象。** 原来管"一个人的信息"，现在管"一个组织的事务"——采集、理解、排序、落事、留痕这五步，一步没变；变的是每条信息后面挂着的是"我"还是"我们部门"。

---

## 1. 三条改造原则

1. **不重写。** InfoAgent 已有的采集、解析、检索、待办、日程全部保留，改的是数据归属和界面视角。
2. **只加一条新链路。** 真正的新东西只有"跨校对标"（公众号采集）。其余都是换皮换语义。
3. **数据不出机器。** 学生会的通知里有人名、手机号、内部安排，云端同步一律不做。

---

## 2. 六个功能模块（按优先级）

| | 模块 | 一句话 | 输入 | 输出 | 改造量 |
|---|---|---|---|---|---|
| M1 | **收件台** | 校内通知汇到一处，筛成"今天该办什么" | 邮箱、QQ 群、微信群 | 待办清单＋责任人 | 小（已有） |
| M2 | **对标库** | 兄弟高校同类活动怎么做的，随时可查 | 公众号、官网 | 可检索的案例卡 | **大（新增）** |
| M3 | **筹备台** | 一场活动从立项到复盘，倒排期 | 活动信息 | 任务、截止、材料清单 | 中 |
| M4 | **资料问答** | 章程、场地规定、报销流程，问一句就答，带原文 | 往届策划、制度文件 | 带出处的回答 | 中（已有 RAG） |
| M5 | **方案体检** | 定稿前告诉你这类活动通常死在哪 | 方案文本 | 带出处的风险清单 | 中（复用 antipode） |
| M6 | **交接档案** | 换届不断档 | 全年沉淀 | 可查的工作档案 | 小 |

### M1 收件台

现有能力直接用：IMAP 只读接入、五分类、截止时间抽取、评分排序。

**行政版要改两处**：

- 分类里加"需转交"——很多通知不是自己办，是转给某个部门，系统要给出建议接收人；
- 待办从"我的"变成"部门的"，每条带责任人、状态（未领／在办／已交）。

### M2 对标库

详见第 3 节。

### M3 筹备台

把 M1 的待办升格成项目：一场歌手赛拆成宣传、场地、物资、评委、彩排、报销六条线，每条线有截止和负责人。时间轴倒排（活动日往前推），不是正排。

**价值**：现在筹备靠一个 Excel 加群里的口头约定，谁负责哪块全靠记。倒排期把"什么时候必须做完什么"变成系统算出来的，不靠人想。

### M4 资料问答

InfoAgent 的 Hybrid RAG 原样搬过来，换语料：往届策划书、场地申请规定、报销流程、章程。

**行政场景的第一个真实问题通常是**："去年迎新是谁对接场地的""报销超过 500 要谁签字"——现在的答案是"问上一届"，而上一届已经退了。

### M5 方案体检

复用已开源的 `antipode`：给它一段方案，它去找最有力的反对意见，带论证链和出处。

行政场景的用法不是"抬杠"，是**把往年踩过的坑摆到台面上**：这类活动最常见的失败原因是天气、场地审批、报名人数不足、赞助方临时撤。每条带出处，不是凭空生成。

### M6 交接档案

每条推荐带评分依据，每个活动带完整时间线，每次改动留版本。换届时导出一份交接包，新人不用从头试错。

## 3. 公众号采集专章（主席点的那条）

### 3.1 先把结论说了

**不要去买接口，不要去爬搜狗，也不要逆向微信协议。** 走"关注 → 本地库 → 渲染正文"这条路——今天我在这台机器上实测通了，全程不需要破解任何东西。

原理很简单：**公众号文章本来就会落到关注者的本地微信数据库里。** 用一个学生会工作号关注几十个兄弟高校的学生会公众号，文章天天自己进来，我们只需要读本地库。

### 3.2 四条路，为什么选第一条

| 路线 | 怎么做 | 可行性 | 成本 | 风险 |
|---|---|---|---|---|
| **A 本地微信库**★ | 工作号关注公众号 → 读本地 `biz_message` 库拿标题+链接 → 渲染抓正文 | **已实测通过** | 一个工作号 | 需在专用机器上运行；账号须实名 |
| B 自家公众号后台 | 用学校某个公众号后台的"超链接"搜索功能，能搜到别家号的文章 | 可行但受限 | 需一个公众号权限 | 只能搜近期，翻页靠人工 |
| C 第三方数据服务 | 新榜、清博等付费 API | 稳定 | 每年数千元起 | 数据出境给第三方；采购流程长 |
| D 搜狗微信／协议逆向 | 老办法 | **基本失效** | — | 验证码、封号、法律风险，不建议 |

### 3.3 实测记录（都是真跑出来的数）

| 验证项 | 结果 |
|---|---|
| 本地公众号库 | `biz_message_0.db`，66 个账号、1120 条公众号消息 |
| 其中含文章链接 | **885 条**，均带 `__biz`／`mid`／`idx`／`sn` 完整参数 |
| 直接 HTTP 抓正文 | 返回 200，但只有 2.6 MB 的 JS 外壳，**拿不到正文** |
| 无头浏览器渲染 | **成功**，标题、正文、公众号名全部取到 |

结论一句话：**列表来自本地库，正文必须用真浏览器渲染。** 这两步都不需要任何灰色手段。

### 3.4 采集流程（六步）

```
① 维护关注清单（30 所兄弟高校学生会/研会/团委）
        ↓
② 定时读本地微信库，取新增文章（标题 + 链接 + 时间）
        ↓
③ 去重（按 __biz + mid + idx 唯一键）
        ↓
④ 无头浏览器渲染正文
        ↓
⑤ 抽取结构化字段（见下）
        ↓
⑥ 入对标库，按活动类型聚类
```

### 3.5 抽哪些字段

| 字段 | 说明 |
|---|---|
| 标题、公众号、发布时间、原文链接 | 基础四件，链接必须保留（出处可查的物理基础） |
| 活动类型 | 迎新／比赛／讲座／市集／志愿／招新／晚会／沙龙 |
| 主办单位、面向对象 | 全校／本院／特定年级／校外 |
| 时间、地点、参与方式 | 从正文抽取，抽不到就留空，不猜 |
| 组织形态 | 线上／线下／混合；是否需报名；是否收费 |
| 宣传要点 | 文案的钩子是什么（送票、抽奖、嘉宾、主题） |
| **风险信号** | 二次通知里的"改期""场地变更""活动取消"——这类信号比活动本身更有价值 |

### 3.6 合规边界（写进方案，主动交代）

1. 只读**公开推文**，不抓留言、不抓关注者信息、不抓后台数据；
2. 采集用专用工作号，不碰个人账号；
3. 数据只在本机，不外传、不上云；
4. 引用一律带原文链接，可随时核对。

### 3.7 必须说清的局限

- **关注才可见。** 系统不会"发现"未知公众号，清单必须人工维护。这是硬约束。
- **公众号名和 ID 对不上。** 本地库里存的是 `gh_xxxx` 号，需要建一张对照表把"复旦学生会"和 `gh_xxx` 绑起来，初期人工。
- **正文有噪声。** 排版元素、图片说明、二维码引导关注都要洗掉。
- **频率要克制。** 一个号一天发三条，三十个号一年近三万篇。实际只取"活动通知"类，且每周增量拉一次即可，不必实时。

## 4. 原模块怎么改（对照表）

| InfoAgent 原模块 | 行政版用途 | 改动 |
|---|---|---|
| 邮件接入 | 部门公共邮箱 + 部长个人邮箱（双源） | 加账号，改归属 |
| 邮件理解与推荐 | 通知分类 + 建议接收人 | 加"转交"分类 |
| 反馈学习 | 部门偏好（哪类通知重要） | 权重口径改 |
| 日报 | 今日行政要点，每天早上推给部长 | 换内容模板 |
| 待办 | 部门待办，带责任人 | 加责任人字段 |
| 日程 | 活动日历（避开考试周、撞期检测） | 加撞期检测 |
| 资料库 | 往届策划、制度文件 | 换语料 |
| JARVIS（18 个工具） | 保留，新增两个工具：`query_benchmark`（查对标库）、`add_activity` | 加两个白名单工具 |
| 反推荐（antipode） | 方案体检 | 重建语料 |
| **无** | **跨校采集** | **全新** |

## 5. 分三期做

| 期 | 内容 | 能演示什么 |
|---|---|---|
| **P1** | 收件台 + 对标库（30 个号跑通） | "别校上周办了什么活动"随手可查——这是最能说服人的一次演示 |
| **P2** | 筹备台 + 资料问答 | 一场活动从立项到复盘走完；问"报销怎么走"能答出原文 |
| **P3** | 方案体检 + 交接档案 | 定稿前出风险清单；换届导出交接包 |

**如果时间只够做一件事，做 P1 的对标库。** 它是主席点名要的，也是唯一别人没有的。

---

## 6. 明确不做

- 不做全自动发文、不做公众号代运营（越界且没价值）
- 不做舆情监控（学校有专门口径，碰了容易出事）
- 不做多校共享平台（先证明一个组织能用）
- 不做云端同步（数据敏感）
- 不做聊天机器人式的"万能助手"（教务、成绩、评教这些走官方系统）

---

## 7. 需要组织提供什么

| 事项 | 说明 |
|---|---|
| 一个专用微信号 | 用来关注兄弟高校公众号，实名、专机专用 |
| 一份关注清单 | 先 30 个，覆盖上海主要高校 + 几所外地标杆 |
| 部门公共邮箱 | 支持 IMAP 即可，只读权限 |
| 往届材料 | 策划书、报销单、场地申请，越多越好 |

前三项不到位，系统就是空转。这不是技术问题，是组织愿不愿意给资源的问题。

---

## 8. 可以直接写进申报材料的三句话

1. 跨校信息采集走"关注—本地库—渲染"路线，不依赖任何第三方接口，已实测跑通；
2. 每条结论都可回溯到原文链接，AI 不生成没有出处的内容；
3. 系统本地运行、只读接入，不改变任何现有账号的邮件状态。
